# Ops incident — 2026-08-26: website down (502), Gunicorn worker futex-deadlock

**Timeline (EDT):** first observed Caddy 502 at 02:13 (earlier possible — journal window limited); user reported ~03:20; restarted `arxiv-grader` ~03:30; `/health` 200 confirmed. Daily pipeline (00:30–00:55) ran normally throughout — server, disk (23%), memory all healthy. Outage was web-service-only.

## Root cause chain

1. The single Gunicorn sync worker (`-w 1`, PID 2674533) deadlocked on an internal lock: `/proc/<pid>/wchan` = `futex_wait_queue`, state S, 9 fds, process alive → systemd showed `active (running)` since Aug 14.
2. No `WORKER TIMEOUT` in the journal → Gunicorn's arbiter never saw the worker as stuck (not wedged inside a request; lock-level deadlock — possibly the known logging-lock/signal class).
3. Accept queue filled to its 2048 backlog (`ss` Recv-Q 2049/2048), largely bot traffic → new connections' SYNs dropped → direct `curl 127.0.0.1:5000` timed out rather than refusing.
4. Caddy's upstream is `localhost:5000` → dials IPv6 `[::1]:5000` first (refused — Gunicorn binds IPv4 only), falls back to `127.0.0.1` which hangs on the full queue until the 3s dial limit → every request = 502 in exactly 3.0s, logged misleadingly as the `::1` refusal.

## Diagnosis path (repeatable)

- `curl -w '%{http_code}'` from outside → 502, `Server: Caddy` header → Caddy up, upstream bad.
- `systemctl status arxiv-grader` → active (running) → NOT a dead process.
- `curl -m 5 http://127.0.0.1:5000/health` on the server → timeout (000) + `ss -tlnp` accept-queue full → wedged worker, distinguishable from refused (dead) and 200 (Caddy-side problem).
- Pre-restart forensics: `head -4 /proc/<worker>/status; cat /proc/<worker>/wchan`.

## Impact

- Rating clicks, /manage, /signup all 502 from ≤02:13 to ~03:30 EDT. Two known lost ratings (visible in Caddy log, user re-clicking): QED → 2608.24344 excellent, yuval → 2608.24684 excellent. Other users' overnight clicks (if any) before 02:13 unknown — journal window didn't reach further back.
- Digest generation/email unaffected.

## Root-cause analysis (post-restart)

Confidence-ranked:
1. **Known**: worker main thread blocked forever acquiring a mutex (`wchan: futex_wait_queue`), not I/O. `server.py`'s `_write_lock` ruled out — all uses are exception-safe `with` blocks in a single-threaded sync worker.
2. **Suspicious**: cgroup showed **3 tasks** where arbiter + sync worker = 2 threads. An unidentified extra thread existed (nothing in `server.py` spawns threads — library-origin?). If it wedged while holding the GIL or a logging lock → main thread futex-waits forever. Alternative classic: signal-handler reentrancy on the logging lock.
3. **Definitive secondary finding — the service was log-blind**: unit uses `StandardOutput=append:/var/log/arxiv-grader/server.log`; logrotate renames weekly with no `copytruncate` → after every rotation Gunicorn writes to the deleted inode, visible `server.log` stays 0 bytes (also observed 2026-08-14), journald captures nothing. Any `WORKER TIMEOUT`/traceback evidence was lost — this is why root cause is a ranked guess, not a proof.
4. Possibly not the first occurrence: service was restarted twice within 5 min on 2026-08-14 (09:48 + 09:53) — consistent with a prior manual recovery from a similar hang.

## Fixes applied 2026-08-26

- `systemctl restart arxiv-grader` — service recovered, `/health` 200.
- `copytruncate` added to `/etc/logrotate.d/arxiv-grader` — Gunicorn's fd stays valid across rotation; logs now survive.
- `py-spy` installed in the server venv — **next occurrence: `py-spy dump --pid <worker PID>` BEFORE restarting** to capture the deadlocked stack.
