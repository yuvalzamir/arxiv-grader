# 2026-09-14 — Missing operator run-summary email (2nd Monday in a row)

[[Home]] | [[Operations]] | [[Check Log Skill]] | [[Daily Digest]]

**Status:** open — needs `daily.log` to close.

---

## Symptom

Operator run-summary email (`[Incoming Science] Run complete — …`) not received on
**Mon 2026-09-07** and **Mon 2026-09-14**. Both Mondays. Tue–Fri unaffected.

**User digests were delivered normally on both dates** (confirmed by the operator for
09-14). This is the key discriminator: the pipeline core ran to completion.

---

## What this rules out

Because digests went out, the failure is strictly in the *tail* of `run_all_users.py`,
after the per-user `ThreadPoolExecutor` block:

- ❌ Cron didn't fire
- ❌ Hang in `fetch_papers.py` / `fetch_preprints.py` (unguarded `feedparser.parse()`)
- ❌ Holiday exit at `run_all_users.py:855` (`sys.exit(0)`) — would have skipped digests too
- ❌ Labor Day (only explains 09-07, not 09-14)

## Surviving candidates

`_send_run_summary()` is called at `run_all_users.py:1120` with **no `try`/`except`**.

**A. `_journal_coverage_lines()` raises (leading).** Called at `run_all_users.py:601`,
*outside* the `try` that wraps only the SMTP send. Two reproducible crash modes:

| Input | Exception |
|---|---|
| any paper with `"source": null` → `sorted(buckets.items())` | `TypeError: '<' not supported between instances of 'NoneType' and 'str'` |
| any non-dict entry in `scraped_journals.json` → `p.get(...)` | `AttributeError: 'str' object has no attribute 'get'` |

Both verified by isolated repro 2026-09-14.

*Why Monday:* Monday's `scraped_journals.json` is the week's largest and most diverse
scrape (Fri evening + Sat + Sun accumulation). Journals that publish late-week appear
**only** in the Monday file, so a single malformed record from one of them fails every
Monday and never Tue–Fri. Deterministic weekday correlation fits this cleanly.

**B. SMTP send failed (weaker).** `_send_run_summary` is the **only** remaining sender on a
bare single-attempt `sendmail` — swallowed into `log.error("Failed to send run summary: %s")`.
Fits the symptom, but 421s are load-correlated, not weekday-deterministic; two consecutive
Mondays with a clean Tue–Fri is a poor fit.

---

## The one grep that settles it

```bash
scp root@116.203.255.222:/var/log/arxiv-grader/daily.log ./debugging/daily_log_0914.txt
grep -n "Run summary emailed\|Failed to send run summary\|Traceback\|TypeError\|AttributeError" debugging/daily_log_0914.txt
```

- **Traceback + `TypeError`/`AttributeError`**, no `Run summary emailed` → **A**.
  Corroborating: the batch-fallback alert block (line 1122+) also never runs.
- **`Failed to send run summary: …`** → **B**.
- Neither line present at all → process still wedged in the weekly-digest phase
  (`run_for_user` → `subprocess.run` with no `timeout=`); check `ps aux | grep run_weekly_digest`.

---

## Fixes (pending confirmation)

1. Wrap the `_send_run_summary(...)` call site in `try`/`except` — the operator's alert channel
   must never be able to kill the run.
2. Harden `_journal_coverage_lines()`: skip non-dict entries, coerce `source` to `str`,
   and wrap the whole body so a bad coverage table degrades to a missing table, not a crash.
3. Give `_send_run_summary` the `_smtp_send_with_retry` helper that `run_daily.py:93` and
   `run_weekly_digest.py:101` already use.
